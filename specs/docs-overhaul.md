## 1. Summary

**Overall state.** The SDK setup and CLI pages are mostly correct. The Cloud pages and the Guides are not.
The Guides section describes a scoring model, a UI and features that Xping Cloud does not have.

Option names and defaults in the configuration reference match the code. The CLI reference
samples are generated by the real renderer and guarded by `DocumentedSampleTests`. Most of the damage
is in text that no test guards: prose, invented log lines, UI walkthroughs and hand-written JSON.

**Worst problems** (by user impact):

1. **Invariant 2 is broken across Guides.** Five pages define "flaky" as "confidence score below 0.60". Flaky
   is a separate classifier verdict. A score below 0.75 (`Reliable`) is only one of three ways a test gets
   *routed* into detection. The other two are an existing flag and retry recovery
   (`dashboard/src/Services/Xping.Analytics/.../FlakyDetectionEligibility.cs:44-50`). A test that retries
   hide can score high and still be flaky. The dashboard decision record
   `docs/decisions/confidence-score-vs-flaky-detection.md` still says 0.60, so the error probably started there.
2. **The confidence score model is wrong everywhere it is described** (`index.md`, understanding-confidence-scores,
   interpreting-test-results, pattern pages):
   - The pages show additive weights 35/20/15/15/10/5. The real model is a Pass Rate level discounted by five factors with
     caps of 0.25/0.20/0.15/0.10/0.10.
   - "Dependency Impact" is not a score factor. It is a flaky-detection classifier. The sixth score factor is Concurrency Sensitivity.
   - The pages say a score needs 10 executions. It needs ESS ≥ 10.
   - The pages say confidence levels are Low/Medium/High at 25/50/100 runs. The real levels are EvidenceLevel `Sparse`/`Adequate`/`Robust` (ESS cut-offs 15 and 40).
3. **UI that does not exist.** The pages describe a four-tab Home, a "Flaky Tests" tab, a filter panel, sort-by-score and trend arrows.
   Both screenshots show the old UI.
4. **Unshipped features described as available**: quarantine (only a disabled "coming soon" button exists),
   notifications and alerts (the wizard is not mounted anywhere), "block PRs below a score" (merge gating is out of scope,
   and this also breaks invariants 2 and 5), and session-reliability presets (removed in dashboard `caaa4bd67`, 2026-08-27; α is now fixed at 0.6).
5. **Install commands fail today.** nuget.org has only prereleases (`1.0.0-rc2` … `rc.8`). Without `--prerelease`, these commands fail:
   - `dotnet add package`
   - `dotnet tool install -g Xping.Cli`
   - `Version="1.0.*"`
6. **The local store privacy text is wrong.** local-store.md says error text, stack traces, machine name and CI
   actor email are not stored. Since #136 they are stored. `index.md` says "no PII", but `CollectCiActorEmail` defaults to true.
7. **Snippets that do not compile, or keys that bind to nothing**:
   - **Unknown key:** `FlushIntervalSeconds` is used in 8 JSON examples, but no such key exists. The real key is `FlushInterval`.
   - **Do not compile:**
     - MSTest "Approach B";
     - the `TryBuild` sample;
     - `var event = …` on both pattern pages;
     - the debugging page's `LogLevel` / `IXpingLogger` API, which does not exist.
   - **Breaks the build:** the NUnit quickstart's `<Compile Include="AssemblyInfo.cs"/>` (NETSDK1022).
   - **Records nothing:** the `index.md` NUnit tab shows only `[assembly: XpingTrack]`.
8. **Invented log and error text** on the configuration, common-issues and debugging pages. The real log format is
   `[Xping HH:mm:ss LVL]`. No grep filter on those pages can match it.
9. **Duplication.** The performance content exists twice: three pages under Guides/Optimization and two under Performance.
   Most of the benchmark numbers come from no artifact, or from Jan-2026 code on .NET 9.
10. **Pages missing from nav.** `known-limitations.md` is in no toc. Users reach it only through links. `versioning.md` is in no toc but is still
    published, and it describes a release flow that `scripts/release.py` replaced.
11. **API reference** leaves out `Xping.Sdk.XUnit.V3` (`docs/docfx.json:7-11`).

### 3.1 Home and Get started

Checked against `main` @ 444389e. Paths are relative to `/Users/adrian/Dev/xping/sdk-dotnet` unless they start with `dashboard/`, which means `/Users/adrian/Dev/xping/dashboard`.

**Applies to every page here: the install commands fail as written.** nuget.org has only prereleases of all six packages (`1.0.0-rc2` … `1.0.0-rc.8`, latest tag `v1.0.0-rc.8` from 2026-11-12, checked through the nuget flat-container API). Three commands break:

Key current facts used throughout:
- Score = `p_shrunk × Π(1 − λ_k(1 − f_k))`. Pass Rate is the **level** (Beta-posterior mean shrunk toward project prior); five **discount** factors with caps λ: Execution Stability 0.25, Environment Consistency 0.20, Concurrency Sensitivity 0.15, Retry Behavior 0.10, Failure Pattern 0.10. Unmeasurable factor discounts nothing. `docs/analytics/xping-confidence-scoring.md:31-60`; `src/Services/Xping.Analytics/appsettings.json:55-63`; `src/Services/Xping.Analytics/Services/ConfidenceScoring/Configuration/ConfidenceScoreConfiguration.cs:50-56`.
- Category bands 0.90 / 0.75 / 0.60 / 0.40 (`ConfidenceScoreConfiguration.cs:561-576`, `appsettings.json` same keys); labels "Insufficient Data / Highly Reliable / Reliable / Moderately Reliable / Unreliable / Highly Unreliable" (`src/Core/Xping.Domain/Entities/Analytics/ScoreCategory.cs:70-79`). Dashboard doc notes thresholds not recalibrated against the composite (#235).
- Insufficient Data = tier-weighted ESS < `MinimumEffectiveSampleSize` 10 inside a 14-day `EvidenceWindow`, not a run count; PR (Speculative) runs weigh 0.3, Untracked 0.5, Canonical 1.0 (`ScoreCategory.cs:30-36`; `ConfidenceScoreConfiguration.cs:192,292`; `src/Core/Xping.Domain/Entities/TestManagement/RevisionTierWeights.cs:15-17`). Scoring lookback 35 days, recency half-life 7 days.
- EvidenceLevel: **Sparse** ESS<15, **Adequate** 15–<40, **Robust** ≥40; null shows "No Data" (`src/Core/Xping.Domain/Entities/Analytics/EvidenceLevel.cs`, `EvidenceLevelThresholds.cs:16,20`). Portal label is "Evidence".
- Trend: OLS slope per day over score history; ±0.005/day significant, ±0.001/day minor, R² ≥ 0.25, ≥5 points (`src/Core/Xping.Domain/Entities/Analytics/ScoreTrend.cs:13-21`; `ConfidenceScoreConfiguration.cs:586-619`).
- Session reliability: `0.6 × EvidenceWeightedMean + 0.4 × Min`, α a **constant** (`src/Core/Xping.Domain/Entities/Analytics/SuiteScoreWeights.cs:65`); evidence weights Sparse 1 / Adequate 2 / Robust 3; unscored tests excluded; revision tier never enters (`src/Services/Xping.Analytics/Services/ConfidenceScoring/SessionConfidenceAggregator.cs:26,71-78,96`). Presets removed in `caaa4bd67` (2026-08-27).
- Flaky classification is classifier vote aggregation (`FlakyDetection:Aggregation:FlakyThreshold` 0.60 is the **vote** threshold, not a score). A score is only an *eligibility* gate: a test is examined if already flagged, OR overall score < 0.75 (`Reliable`), OR it has retry-recovery evidence (`src/Services/Xping.Analytics/Services/FlakyDetection/FlakyDetectionEligibility.cs:43-50`; `src/Services/Xping.Analytics/Functions/ConfidenceScoring/ConfidenceScoreCalculationFunction.cs:56,560`).

#### Key facts from code (they drive most findings)

- **No `FlushIntervalSeconds` key.** The option is `FlushInterval` (TimeSpan, default 30 s). JSON takes `"00:00:30"`; the env var `XPING_FLUSHINTERVAL` takes seconds or a TimeSpan. `src/Xping.Sdk.Core/Configuration/XpingConfiguration.cs:80`, `src/Xping.Sdk.Core/Extensions/XpingServiceCollectionExtensions.cs:668-675`. `FlushIntervalSeconds` in JSON binds to nothing, and nothing warns about it. All 8 JSON examples that use it in the guides do nothing.
- **`BatchSize`**: default 100, range 1–1000 (`XpingConfiguration.cs:73-75`, `:328-336`).
- **Batching and the flush timer exist only in Cloud mode.** `XpingContextOrchestrator.cs:238-257`: the timer and the `BufferFull` handler are wired only when `_mode == XpingMode.Cloud`. In LocalOnly (the default with no API key), nothing uploads, and `BatchSize`/`FlushInterval` have no effect on memory or timing.
- **Memory grows with the whole run.** In every collecting mode, each drained batch is also copied into `_localExecutions`, which holds full `TestExecution` objects (stack traces included) until finalization (`XpingContextOrchestrator.cs:71-78`, `:996`, `:1040-1050`, `:1068-1076`). The collector's `ConcurrentQueue` has no cap (`Services/Collector/Internals/TestExecutionCollector.cs:18`, `:47-55`). So peak memory is about N tests × (size of a TestExecution), whatever `BatchSize` is. "Batch size × 1 KB" and "reduce BatchSize to cut memory" are wrong.
- **The flush partly runs on the test thread.** `BufferFull` is raised synchronously inside `RecordTest` (`TestExecutionCollector.cs:52-55`). Its `async void` handler then drains, builds the session, serializes it and gzips it (`Services/Upload/Internals/XpingUploader.cs:166-175`) on the thread of the test that filled the batch. Only the HTTP send is awaited. Finalization blocks the end of the run: it writes local history synchronously, then uploads, capped at 2 × `UploadTimeout` = 60 s by default (`XpingConfiguration.cs:142-147`, `XpingContextOrchestrator.cs:470-500`). "Zero blocking" is overstated.
- **Hot path per test**: a fingerprint `ConcurrentDictionary.TryAdd`, `Interlocked.Increment`, an enqueue, a count check (`XpingContextOrchestrator.cs:404-428`, `TestExecutionCollector.cs:27-56`), plus `_statisticsAccumulator.Record` (`XpingContextOrchestrator.cs:887-890`). No I/O.
- **Environment info is per session or batch, not per test.** `TestExecution` has no environment fields (`Models/Executions/TestExecution.cs:87-256`). Parameters are kept as `ParameterHash` plus the display name (`TestIdentity.cs:123,136`).
- **Retries**: Polly, exponential with jitter, `MaxRetries` default 3 (0–10), `RetryDelay` default 2 s (`XpingServiceCollectionExtensions.cs:550-560`). `UploadTimeout` default 30 s (1 s – 1 day).
- **`Enabled=false` turns into Mode `Disabled`**: no collection, no local store, no uploads (`XpingMode.cs` `Disabled`). "No network but keep history" is `Mode=LocalOnly` / `XPING_MODE=LocalOnly`.
- **Benchmarks** (`tests/Xping.Sdk.Benchmarks`, net10.0, BenchmarkDotNet **0.15.8**): Collector, Upload, Configuration, EnvironmentDetection, Integration, AdapterIntegration, BatchProcessing, Concurrency, MemoryPressure, StressTest, RealNUnit/RealXUnit/RealMSTest adapter, LocalStore, LocalStoreScan. There is no xUnit v3 benchmark.
- **Committed baseline** `tests/Xping.Sdk.Benchmarks/results/baseline/*` comes from a single commit, df5314c (2026-01-02). It was produced with BenchmarkDotNet 0.14.0 on .NET 9.0.4 / Apple M4 and has never been refreshed. The code has changed since: `ConcurrencyBenchmarks` renamed `ContendedFlush_*`/`MixedOperations_RecordAndFlush_*` to `*Drain*` (`ConcurrencyBenchmarks.cs:198-243`), `AdapterIntegrationBenchmarks.TestsWithSessionContext` became `TestsWithExtensiveMetadata` (`:247`), and the sampling benchmark went away in #155. The baseline also includes `SampleBenchmark`, which has no source file. `BenchmarkDotNet.Artifacts/` is gitignored (`.gitignore:274-275`). The only fresh local artifact is `BenchmarkDotNet.Artifacts/results/*LocalStoreScanBenchmarks*` (2026-10-22, BenchmarkDotNet 0.15.8, .NET 10, M5 Pro), and it is not committed.
- **No CI runs benchmarks.** None of the workflows mention benchmarks (`.github/workflows/{ci,nightly,release,publish-github-packages,cli-credential-stores}.yml`).
- **`UploadBenchmarks` only measures `JsonSerializer.Serialize`** with its own options (`UploadBenchmarks.cs:34-60`). It does no HTTP, no gzip and no `IXpingSerializer`. Every "upload" number is really a serialization number.
- **The "Real*AdapterBenchmarks" don't touch the frameworks.** They build a `TestExecution` with `TestExecutionBuilder` and call `XpingContext.RecordTest` (`RealNUnitAdapterBenchmarks.cs:32-78`). No NUnit, xUnit or MSTest attribute processing, reflection or event mapping is measured.

## 8. Writing rules for every later phase

**Language**

- Readers include non-native English speakers. Write short sentences and plain words. Use no idioms, jokes or metaphors.
- One idea per sentence. One topic per paragraph. Prefer lists and tables to long paragraphs.
- Use the present tense. Describe what the product does now. No history: no "now", "new", "previously", "used to", "since vX", "legacy",
  "deprecated", migration notes or version tags (inv. 7).
- Address the reader as "you". Use the active voice: "The SDK writes the session", not "The session is written".

**Accuracy**

- Every code sample, config snippet, log line and CLI output matches the current code exactly. Copy strings from the source. Never retype them.
  Prefer an `xping:sample` block that `DocumentedSampleTests` guards to a hand-written output block.
- Every C# snippet compiles against the current packages. Every JSON/YAML snippet uses real keys.
- Document only shipped behaviour (inv. 8). If a reader could look for an unshipped feature, say in one line that it is not available. Do not describe it.
- Each phase PR lists, for each changed claim, the code file:line that backs it.

**Product rules** (from the invariants)

- Local runs produce observations and evidence. Never write that the CLI scores a test or names a cause.
- Never connect a score threshold to "flaky". Flaky is a separate verdict.
- Session reliability = α × Mean + (1 − α) × Min, with α = 0.6. Tier weighting applies only to test executions during scoring.
- Confidence, factor scores, ESS and EvidenceLevel are fixed-window values. Never suggest they can be summed or averaged over a custom date range.
- Quarantine and merge gating are separate. Neither is shipped.
- Exit codes are an API: list every code a command can return. Say which output goes to stdout (data) and which to stderr (everything else).
- The product is "Xping Cloud". Never "Dashboard", in text or image file names.
- No Portal screenshots and no Portal navigation tours (C2). A task page may give one path to the setting it needs (for example, Settings → API keys).
- No benchmark numbers on the user site (P1).
- The flaky routing sentence is always: "Cloud examines tests that score below Reliable, are already flagged, or recovered on a retry." (C5)

**Glossary** (define each term once, on the page in brackets; link to it elsewhere; never use a synonym):

| Term | Meaning | Defined on |
|---|---|---|
| test run / session | One `dotnet test` invocation recorded by the SDK. Pick one word in P12 and use it everywhere. The code uses "session" and the CLI says "runs". | collected-data |
| execution | One test's result within a session. | collected-data |
| local store | The folder where the SDK writes sessions and the CLI reads them. | local-store |
| finding | Something `xping report` observed in local history, with a kind. | reading-the-report |
| finding kind | One of the 13 `FindingKind` values. | reading-the-report |
| evidence (local) | How much local history supports a finding: `sparse` / `adequate` / `robust`. It uses the same labels as Cloud's EvidenceLevel (L7), with its own cut-offs. | reading-the-report |
| confidence score | Xping Cloud's 0–1 reliability estimate for a test, over a fixed window. | confidence-scores |
| factor | One of the 6 inputs to the confidence score. | confidence-scores |
| ESS | Effective sample size: weighted run count behind a score. | confidence-scores |
| EvidenceLevel | Sparse / Adequate / Robust, from ESS. | confidence-scores |
| score category | Highly Reliable … Highly Unreliable, or Insufficient Data. | confidence-scores |

**Form**

- Each page starts with one sentence saying what the page covers and who it is for.

- Link to the reference instead of repeating an option table. Each fact lives on one page.
- Each page sets `uid` and `title` in front matter.
